# Database Schema Documentation

This document describes the initial SQLite tables for corpus identity and
uploaded source files. All timestamps use ISO-8601 UTC
text generated by the application, for example `2026-08-02T12:34:56Z`.

The backend stores the local development database in
`backend/rag_playground.sqlite3`. The database is initialized from
`schema.sql` when the ingestion routes first access it. This file is ignored by
Git because it contains local user data.

## `corpus`

Represents the user-facing, named body of knowledge. Users create a new corpus
when they want a separate document collection.

| Field | Description |
| --- | --- |
| `id` | Stable application-generated identifier for the corpus. Primary key. |
| `name` | User-provided name displayed in the application. |
| `description` | Optional explanation of the corpus's purpose or contents. |
| `created_at` | UTC timestamp when the corpus was created. |
| `updated_at` | UTC timestamp when mutable corpus metadata was last changed. |

## `document`

Represents one physically stored, immutable uploaded source file belonging to a
single corpus.

| Field | Description |
| --- | --- |
| `id` | Stable application-generated identifier for the uploaded file. Primary key. |
| `corpus_id` | Identifier of the corpus that owns the document. Foreign key to `corpus.id`. |
| `original_filename` | Filename supplied by the user, retained for display. |
| `storage_path` | Filesystem path or object-store key for the single persisted source file. Unique. |
| `mime_type` | Detected media type when server-side detection is added; currently absent. |
| `size_bytes` | Byte length of the stored source file. Must be zero or greater. |
| `content_sha256` | SHA-256 digest of file contents for integrity checks and future deduplication. |
| `uploaded_at` | UTC timestamp when the application accepted the source file. |

## Operational Note

SQLite foreign-key checks are disabled by default. Every application connection
must execute `PRAGMA foreign_keys = ON` before using these tables.

The `POST /uploads` route creates one corpus per upload request and one document
row per validated file. Files are stored under `backend/uploads/` with UUID-based
names; `original_filename` remains available for display. The `GET /corpora/`
route returns the persisted corpus and nested document records.
