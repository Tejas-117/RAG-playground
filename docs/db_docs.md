# Database Schema Documentation

This document describes the SQLite tables for corpus identity, uploaded source
files, reusable chunking artifacts, and immutable pipeline runs. All timestamps
use ISO-8601 UTC text generated by the application, for example
`2026-08-02T12:34:56Z`.

The backend stores the local development database in
`backend/rag_playground.sqlite3`. The database is initialized from
`schema.sql` when the ingestion routes first access it. This file is ignored by
Git because it contains local user data.

## `corpus`

Represents the user-facing, named body of knowledge. Users create a new corpus
when they want a separate document collection.

| Field | Description |
| --- | --- |
| `id` | Stable application-generated identifier for the corpus. Primary key. |
| `name` | User-provided name displayed in the application. |
| `description` | Optional explanation of the corpus's purpose or contents. |
| `created_at` | UTC timestamp when the corpus was created. |
| `updated_at` | UTC timestamp when mutable corpus metadata was last changed. |

## `document`

Represents one physically stored, immutable uploaded source file belonging to a
single corpus.

| Field | Description |
| --- | --- |
| `id` | Stable application-generated identifier for the uploaded file. Primary key. |
| `corpus_id` | Identifier of the corpus that owns the document. Foreign key to `corpus.id`. |
| `original_filename` | Filename supplied by the user, retained for display. |
| `storage_path` | Filesystem path or object-store key for the single persisted source file. Unique. |
| `mime_type` | Detected media type when server-side detection is added; currently absent. |
| `size_bytes` | Byte length of the stored source file. Must be zero or greater. |
| `content_sha256` | SHA-256 digest of file contents for integrity checks and future deduplication. |
| `uploaded_at` | UTC timestamp when the application accepted the source file. |

## `chunk_set`

Represents the complete, reusable result of applying one exact chunking
configuration to one immutable corpus. It is an artifact record, not a mutable
user configuration. The unique `fingerprint` is calculated from the immutable
corpus, the normalized chunking configuration, and the chunker
implementation/version. A later run with the same fingerprint can reuse this
result rather than split the documents again.

| Field | Description |
| --- | --- |
| `id` | Stable application-generated identifier for the chunking artifact. Primary key. |
| `corpus_id` | Immutable corpus used to create the artifact. Foreign key to `corpus.id`. |
| `fingerprint` | Deterministic, unique cache identity for the exact upstream inputs and configuration. |
| `chunking_config_json` | Canonical serialized `ChunkingConfig`, including resolved defaults. |
| `chunker_name` / `chunker_version` | Implementation identity so changed chunking code cannot silently reuse old output. |
| `status` | Build lifecycle: `pending`, `running`, `ready`, or `failed`. |
| `chunk_count` | Number of child `chunk` rows once the build completes. |
| `created_at`, `started_at`, `completed_at` | UTC lifecycle timestamps. `started_at` and `completed_at` are absent until reached. |
| `duration_ms` | Completed stage duration in milliseconds when known. |
| `error_code` / `error_details_json` | Structured failure information, populated only when the build fails. |

## `chunk`

Represents one ordered text segment within a `chunk_set`. Chunk rows and their
source provenance live in SQLite; vector embeddings and vector-search indexes
will live in Chroma and refer back to this stable `chunk.id`.

| Field | Description |
| --- | --- |
| `id` | Stable application-generated chunk identifier. Primary key and future vector-store ID. |
| `chunk_set_id` | Chunking artifact that produced this chunk. Foreign key to `chunk_set.id`. |
| `source_document_id` | Original uploaded document from which the text came. Foreign key to `document.id`. |
| `ordinal` | Zero-based position among chunks from this source document within this chunk set. Unique with `chunk_set_id` and `source_document_id`. |
| `text` | Chunk text sent to the embedding stage and supplied as retrieval context. |
| `character_start_offset` / `character_end_offset` | Optional zero-based offsets into normalized parsed text; end offset is not before start. |
| `token_start_offset` / `token_end_offset` | Optional zero-based offsets in the configured tokenizer; end offset is not before start. |
| `page_start` / `page_end` | Optional one-based source page range. |
| `section_path_json` | Optional ordered heading/section path for source display and filtering. |
| `source_metadata_json` | Non-null JSON object containing parser/source metadata retained for provenance. |

Parsing executes during upload. Chunking executes from `POST /runs` and writes
or reuses these persisted artifacts before the run completes.

## `pipeline_run`

Represents one immutable single-question run submitted from the experiment
workbench. The current endpoint executes through chunking; embedding, retrieval,
generation, and evaluation remain unimplemented.

| Field | Description |
| --- | --- |
| `id` | Stable application-generated identifier for the run. Primary key. |
| `corpus_id` | Immutable corpus selected for the run. Foreign key to `corpus.id`. |
| `chunk_set_id` | Nullable while execution is pending or failed; completed runs reference the exact ready `chunk_set` they used. |
| `question` | Trimmed, non-empty question submitted by the user. |
| `effective_config_json` | Canonical JSON snapshot of the complete typed pipeline configuration, including resolved defaults. |
| `status` | Run lifecycle: `pending`, `running`, `completed`, or `failed`. |
| `chunk_set_reused` | Nullable until chunking succeeds; records whether this execution reused an existing ready artifact. |
| `created_at`, `started_at`, `completed_at` | UTC lifecycle timestamps. |
| `duration_ms` | Total execution duration through the currently implemented chunking stage. |
| `error_code` / `error_details_json` | Safe structured terminal failure information without raw traces. |

The question belongs to the run because it is query-specific. It is not stored
on `corpus`, `document`, or `chunk_set`. Identical submissions create separate
run rows, but their `chunk_set_id` values may match when the reusable fingerprint
matches. Failures after creation remain as `failed` runs for auditability.

## Operational Note

SQLite foreign-key checks are disabled by default. Every application connection
must execute `PRAGMA foreign_keys = ON` before using these tables.

The `POST /uploads` route creates one corpus per upload request and one document
row per validated file. Files are stored under `backend/uploads/` with UUID-based
names; `original_filename` remains available for display. The `GET /corpora/`
route returns the persisted corpus and nested document records.

The `POST /runs` route validates a selected corpus, a single question, and the
complete pipeline configuration. `PipelineExecutor` creates the lifecycle row,
builds or reuses its chunk set in a worker thread, and stores the artifact link
before returning. The snapshot includes optional retrieval and answer metric
lists, but no later pipeline stages or evaluation results execute yet.

The development database has no migration compatibility guarantee at this
stage. After a breaking schema edit, `backend/rag_playground.sqlite3` may be
recreated; uploaded source files are separate and need not be deleted.
