# Database Schema Documentation

This document describes the SQLite tables for corpus identity, uploaded source
files, reusable chunking/vector artifacts, retrieval and generation results,
and immutable pipeline runs. All timestamps use ISO-8601 UTC text generated by the application, for example
`2026-08-02T12:34:56Z`.

The backend stores the local development database in
`backend/rag_playground.sqlite3`. The database is initialized from
`schema.sql` when the ingestion routes first access it. This file is ignored by
Git because it contains local user data.

## `corpus`

Represents the user-facing, named body of knowledge. Users create a new corpus
when they want a separate document collection.

| Field | Description |
| --- | --- |
| `id` | Stable application-generated identifier for the corpus. Primary key. |
| `name` | User-provided name displayed in the application. |
| `description` | Optional explanation of the corpus's purpose or contents. |
| `created_at` | UTC timestamp when the corpus was created. |
| `updated_at` | UTC timestamp when mutable corpus metadata was last changed. |

## `document`

Represents one physically stored, immutable uploaded source file belonging to a
single corpus.

| Field | Description |
| --- | --- |
| `id` | Stable application-generated identifier for the uploaded file. Primary key. |
| `corpus_id` | Identifier of the corpus that owns the document. Foreign key to `corpus.id`. |
| `original_filename` | Filename supplied by the user, retained for display. |
| `storage_path` | Filesystem path or object-store key for the single persisted source file. Unique. |
| `mime_type` | Detected media type when server-side detection is added; currently absent. |
| `size_bytes` | Byte length of the stored source file. Must be zero or greater. |
| `content_sha256` | SHA-256 digest of file contents for integrity checks and future deduplication. |
| `uploaded_at` | UTC timestamp when the application accepted the source file. |

## `chunk_set`

Represents the complete, reusable result of applying one exact chunking
configuration to one immutable corpus. It is an artifact record, not a mutable
user configuration. The unique `fingerprint` is calculated from the immutable
corpus, the normalized chunking configuration, and the chunker
implementation/version. A later run with the same fingerprint can reuse this
result rather than split the documents again.

| Field | Description |
| --- | --- |
| `id` | Stable application-generated identifier for the chunking artifact. Primary key. |
| `corpus_id` | Immutable corpus used to create the artifact. Foreign key to `corpus.id`. |
| `fingerprint` | Deterministic, unique cache identity for the exact upstream inputs and configuration. |
| `chunking_config_json` | Canonical serialized `ChunkingConfig`, including resolved defaults. |
| `chunker_name` / `chunker_version` | Implementation identity so changed chunking code cannot silently reuse old output. |
| `status` | Build lifecycle: `pending`, `running`, `ready`, or `failed`. |
| `chunk_count` | Number of child `chunk` rows once the build completes. |
| `created_at`, `started_at`, `completed_at` | UTC lifecycle timestamps. `started_at` and `completed_at` are absent until reached. |
| `duration_ms` | Completed stage duration in milliseconds when known. |
| `error_code` / `error_details_json` | Structured failure information, populated only when the build fails. |

## `chunk`

Represents one ordered text segment within a `chunk_set`. Chunk rows and their
source provenance live in SQLite; vector coordinates live in Chroma and refer
back to this stable `chunk.id`.

| Field | Description |
| --- | --- |
| `id` | Stable application-generated chunk identifier. Primary key and future vector-store ID. |
| `chunk_set_id` | Chunking artifact that produced this chunk. Foreign key to `chunk_set.id`. |
| `source_document_id` | Original uploaded document from which the text came. Foreign key to `document.id`. |
| `ordinal` | Zero-based position among chunks from this source document within this chunk set. Unique with `chunk_set_id` and `source_document_id`. |
| `text` | Chunk text sent to the embedding stage and supplied as retrieval context. |
| `character_start_offset` / `character_end_offset` | Optional zero-based offsets into normalized parsed text; end offset is not before start. |
| `token_start_offset` / `token_end_offset` | Optional zero-based offsets in the configured tokenizer; end offset is not before start. |
| `page_start` / `page_end` | Optional one-based source page range. |
| `section_path_json` | Optional ordered heading/section path for source display and filtering. |
| `source_metadata_json` | Non-null JSON object containing parser/source metadata retained for provenance. |

Parsing executes during upload. A prepared-index request invokes chunking and
writes or reuses this artifact before embedding begins.

## `vector_index`

Represents one complete reusable embedding space for an exact chunk artifact.
SQLite stores compatibility and lifecycle provenance; the vector coordinates
remain in the named Chroma collection.

| Field | Description |
| --- | --- |
| `id` | Stable deterministic identifier for the ready vector-index artifact. |
| `chunk_set_id` | Exact ready chunk artifact embedded by this index. |
| `fingerprint` | Unique compatibility hash covering upstream, model, dimensions, policy, metric, and indexer inputs. |
| `embedding_config_json` | Canonical resolved provider, model, and distance configuration. |
| `provider` / `model` | Provider and model identifiers selected by the run. |
| `provider_model` / `provider_revision` | Optional model provenance reported by the provider response. |
| `dimensions` | Positive shared width of every stored vector. |
| `distance_metric` | `cosine`, `dot_product`, or `euclidean`. |
| `input_policy_version` | Versioned document/query text-prefix policy. |
| `indexer_name` / `indexer_version` | Vector-store implementation identity. |
| `collection_name` | Unique Chroma collection containing explicit vectors. |
| `status` | Always `ready`; partial builds are never inserted into SQLite. |
| `vector_count` | Verified number of records stored in Chroma. |
| `created_at`, `started_at`, `completed_at`, `duration_ms` | Artifact lifecycle and measured build time. |

## `benchmark_run` and `benchmark_example_run`

`benchmark_run` is the single user-visible execution launched from the
experiment workbench. It references one ready named index and one immutable
evaluation dataset, records their shared corpus and technical vector index, and
stores the complete effective configuration snapshot. Progress uses total and
completed example counts plus the active example and query-time stage.

`benchmark_example_run` is an internal ordered child for one stable
`evaluation_example`. It stores independent lifecycle, stage timings, and safe
failure details without presenting each question as a separate top-level run.
Earlier completed children remain inspectable if a later question fails.

Query-time artifacts use `benchmark_retrieval_result`,
`benchmark_retrieved_chunk`, `benchmark_generation_result`, and
`benchmark_generation_context_chunk`. They retain raw distances, source chunks,
provider provenance, and exact prompt-context links under each child execution.

## `prepared_index`

Represents one user-facing named request to prepare an immutable corpus through
chunking and embedding. It also acts as the durable asynchronous job record, so
the worker can recover its instructions after the HTTP request has ended or the
backend has restarted.

| Field | Description |
| --- | --- |
| `id` | Stable application-generated selection identity. |
| `name` | Trimmed user-facing label, limited to 100 characters. It is intentionally not unique. |
| `corpus_id` | Immutable corpus to prepare. |
| `effective_config_json` | Canonical immutable snapshot of resolved chunking and embedding configuration. |
| `chunk_set_id` | Exact ready chunk artifact after chunking succeeds; nullable before then. |
| `vector_index_id` | Exact ready technical vector artifact after embedding succeeds; nullable before then. |
| `status` | `pending`, `running`, `ready`, or `failed`. |
| `current_stage` | `chunking` or `embedding` while running; otherwise null. |
| `chunk_set_reused` / `vector_index_reused` | Whether each compatible artifact existed before this request. |
| `chunking_duration_ms` / `embedding_duration_ms` | Time this request spent resolving each stage. |
| `created_at`, `started_at`, `completed_at`, `duration_ms` | Durable queue and execution lifecycle. |
| `error_code` / `error_details_json` | Safe structured terminal failure details. |

Configuration is stored on this row because a pending worker must know what to
build before the referenced artifacts exist. After completion, `chunk_set` and
`vector_index` retain their own technical compatibility configurations. This is
small provenance duplication; chunks remain only in `chunk`, and vectors remain
only in the vector store.

Different prepared-index IDs and duplicate names can reference the same
`vector_index_id` when their corpus, chunking, embedding, provider policy,
dimensions, distance metric, and indexer inputs are compatible.

## Operational Note

SQLite foreign-key checks are disabled by default. Every application connection
must execute `PRAGMA foreign_keys = ON` before using these tables.

The `POST /uploads` route creates one corpus per upload request and one document
row per validated file. Files are stored under `backend/uploads/` with UUID-based
names; `original_filename` remains available for display. The `GET /corpora/`
route returns the persisted corpus and nested document records.

The `POST /indexes` route validates a required name, corpus, and chunking plus
embedding configuration, then returns `202` with a pending durable request.
`GET /indexes` lists newest records and accepts an optional `status` filter.
`GET /indexes/{prepared_index_id}` returns one pollable lifecycle record. The
application worker chooses the oldest pending job across prepared indexes and
dataset benchmarks so local provider workloads do not compete. A restart marks
abandoned running jobs as failed with a structured error.

The `POST /runs` route validates a ready prepared index, a compatible evaluation
dataset, and query-time configuration. It stores one pending benchmark with an
ordered child execution for every dataset example and returns `202`. The worker
retrieves and generates for each child against the selected vector index.
`GET /runs` lists benchmark summaries, while `GET /runs/{run_id}` returns the
benchmark lifecycle and its question-level outputs.

The development database has no migration compatibility guarantee at this
stage. After this schema edit, recreate `backend/rag_playground.sqlite3` before
starting the backend. Uploaded source files are separate. Local Chroma data is
stored under the ignored `backend/chroma_data/` directory by default.
